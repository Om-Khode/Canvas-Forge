# ADR 006 - Element grouping: baked transforms, with the group as an element variant

**Status:** accepted, implemented
**Code:** `src/features/elements/tree.ts`, `group.ts`, `reparent.ts`, `src/store/deriveGroups.ts`, `src/features/selection/resolve.ts`, `gestureTargets.ts`
**Amends:** `docs/data-model.md` §3, `docs/architecture.md` §2, `docs/export.md` §2–3

## Problem

The document was a flat list. Every element was a sibling of every other, depth was an index in one array, and there was no way to treat several elements as one thing - no way to name a cluster, move it as a unit, or fold it behind a single row in the layers panel.

This was the largest remaining feature and the only one that changes contracts the project had treated as frozen: `CanvasElement`, `ElementStore`, and the serialized schema. Grouping is also the feature where the naive implementation is famously wrong in an interesting way, because "a group" can mean at least three different data structures with three different costs.

## Options considered

**Groups as a separate container map.** `ElementStore` gains a `groups` record and `order` becomes a tree of nodes rather than a list of element ids. `CanvasElement` is untouched: no drawer, no hit-test change, no new `switch` case anywhere.

**A true nested transform scene graph.** Groups own a transform, children are stored in parent-local space, and matrices compose down the tree at draw and hit-test time. This is the mathematically correct answer and the one a full vector editor eventually needs - it handles a rotated child inside a rotated parent exactly.

**Baked transforms, with the group as a variant of `CanvasElement`.** A group has no transform of its own. Its box is the axis-aligned union of its descendants, and transforming a group writes the transform straight into every descendant. `GroupElement extends BaseElement` and joins the union; membership is a `childIds` array on the group.

## Decision

Baked transforms, with the group as a variant of `CanvasElement`.

```ts
export interface GroupElement extends BaseElement {
  readonly type: 'group';
  /** Members, bottom-to-top within the group. */
  readonly childIds: readonly ElementId[];
}
```

`ElementStore.order` narrows to **root-level ids only**; membership lives on the group. Paint order becomes a depth-first walk (`tree.ts`, `elementsToPaint`) instead of a `map` over `order`.

## Why

**The hard mathematics already existed, and was already tested.** `rotateElements(elements, centerWorld, radians)` advances each element's own angle *and* orbits its centre - that is group rotation. `resizeElements` scales each member proportionally inside a shared box - that is group resize. Group transform and multi-selection transform are the same operation; grouping only gives that operation a persistent name. Not one line of new transform mathematics was written for this feature, and `store.test.ts` pins the claim rather than asserting it in prose: `translateElements(gestureTargets(store, [groupId]), 7, 11)` produces a patch map `toEqual` the one produced by translating the two members directly.

**Making the group an element inherits everything downstream.** `name`, `visible`, `locked`, `opacity`, z-order and the layers-panel row all come from `BaseElement`, because every consumer already works on "a thing with an id that appears in the order". The separate-container-map option keeps `CanvasElement` clean and pays for it forever: selection becomes `Set<ElementId | GroupId>`, and naming, visibility, locking and z-order each need a parallel implementation. It trades a handful of compiler-guided `switch` cases for a permanent second kind of thing.

**The cost of the union change is bounded and the compiler enumerates it.** Every exhaustive `switch` on `element.type` must now handle a variant that draws nothing. That is `assertNever` doing exactly the job it was added for: the compiler produced the work list instead of a human grepping for it. `drawers/group.ts` is the whole rendering change - `export function drawGroup(): void {}` - and it exists so the dispatcher stays exhaustive rather than special-casing the one variant with no geometry.

**The scene graph was rejected on blast radius, not on correctness.** It is the better model. It also breaks every site that assumes `element.x` is a world coordinate: hit-testing, bounds, alignment, export, the properties panel's X/Y, marquee. Worse for this codebase specifically, it would blur the meaning of the branded `WorldPoint` and `ScreenPoint` types that currently make coordinate-space mistakes a compile error (`docs/coordinate-system.md`) - an element's `x` would sometimes be world and sometimes parent-local, with nothing in the type system to say which. That is most of the codebase, spent to buy correctness in a case Figma itself does not handle.

## Trade-offs

**Resizing a rotated group is approximate.** Descendants scale in the group's axis-aligned frame, so a rotated child can shear slightly. Figma has this exact limitation, and it is the same trade already documented for multi-selection resize in `docs/data-model.md`. This is the price of baking, and it is the whole price.

**A group's geometry is derived state stored in the same fields as authored state.** `x`, `y`, `width`, `height` on a `GroupElement` are a cache of the union of its *leaf* descendants; `rotation` is 0. Storing derived values invites drift, and that is a real wart. The alternative - a narrower base type for groups - makes the union non-uniform and forces narrowing at every `element.x` in the codebase. The union stays uniform and the drift is prevented in exactly one place instead: `withDerivedGroups` on the store's single write path.

**Reparenting is a layers-panel gesture, not a canvas gesture.** Dragging an element into or out of a group on the canvas needs drop-target detection and a live preview, and reads as broken at 90% complete. Ctrl+G, Ctrl+Shift+G and drag in the layers panel are the routes; canvas drag-to-reparent is listed as future work rather than half-built.

**Ungrouping *k* groups costs O(k·n) map copies.** `ungroupElements` rebuilds `byId` once per group in the selection. Fine for a keystroke's worth of selection; worth revisiting if `k` ever comes from something like select-all on a document made mostly of groups. The comment saying so is in the source, not only here.

## Consequences

### The derived-geometry invariant is the load-bearing idea, and it bites first

A group's box is output, never input. `withDerivedGroups` (`src/store/deriveGroups.ts`) runs on the elements slice's single write path and re-derives every group's box from its leaves, dissolves groups with no live members, and enforces one-home-per-element.

The first consequence of that is counter-intuitive enough that it was raised as a hazard, traced through the code by a review, and closed before it ever reached a browser: **the obvious implementation of a group drag moves nothing at all.** The interaction layer snapshotted the selected elements - with a group selected, that is the group - and `translate` patched the group's `x`/`y`. `withDerivedGroups` then recomputed that same box from the unmoved leaves *inside the same synchronous write*, erasing the patch. Resize and rotate took the identical path.

The fix is not a special case; it is the model stated correctly. `transformSet` (`features/selection/resolve.ts`) expands a selection down to its leaves, which are the only elements holding real geometry, and the leaves are what the transform patches. The group's box then follows, because that is what a cache does.

The general lesson is worth keeping: *a cache recomputed on the write path silently reverts any write aimed at the cache.* The failure mode is not a wrong value but no value - the gesture appears inert, which reads as a dead event handler rather than as a data-model problem.

### `order` changed meaning, and twelve call sites broke without a single test failing

Narrowing `ElementStore.order` to root ids is a one-line change to a type comment. It silently changed the answer of `elementsInOrder`, the selector twelve production call sites used to mean "every element in the document". After grouping, it meant "every root element".

None of the roughly 900 tests in the suite failed. The reason is structural, not an oversight: **the tests build `ElementStore` literals directly and assert on the modules under test, so almost none of them route through the selector.** A selector whose *inputs* are unchanged and whose *contract* changed is invisible to tests written that way.

All twelve sites were found by code review, and the three that mattered most were found from three unrelated directions in three separate reviews:

- the SVG export review noticed grouped content missing from the file;
- the transform task independently hit the PNG side of the same call site in `ExportDialog.tsx`;
- the review of *that* task found the minimap, which built its scene from the flat array and so drew a blank map for a grouped document - grouped content painted on canvas and vanished in the overview.

The remedial sweep (`8579cdc`) fixed seven of them, verified one - select-all, where root ids are the correct answer - and pinned it with a test so a later sweep does not "fix" it. The three export shapes that consumers actually need now live in `features/export/scope.ts` with their own tests, because "which walk does this caller want" turned out to have three different right answers and was being re-derived at each call site.

The generalizable point: **broadening a type is caught by the compiler; narrowing the meaning of a value inside an unchanged type is caught by nothing.** A test suite that constructs its own fixtures is blind to it by construction, and that is a coverage shape, not a coverage number.

### Cycle guards are correctness, not defensive programming

`childIds` is data. It survives a round trip through a project file, so a group that lists itself - or two groups that list each other - is a document that can exist. Every tree walk in `tree.ts` therefore carries a shared `visited` set, and `walkChildren`'s is doubly load-bearing: it is the crash guard *and* it is the mechanism that makes "emit each id once" true. `leavesOf` passes one set across the whole call, which is why a selection naming both a group and one of its own members yields each leaf exactly once instead of transforming it twice.

The sharpest instance is that `wouldCreateCycle` is built on `descendantsOf`. Without the guard, the cycle *detector* would be the first thing to fall over on a store that already contains one.

The same reasoning propagates to every hand-written recursion over the tree: `serialize.ts`'s writer, `svg.ts`'s `rendered` set, `layerRows.ts`'s row builder, `elementsToPaint`'s walk. Each carries its own guard with a comment saying why, and the SVG exporter's is deliberately *one* set for the whole export rather than one per root - a per-path set would stop a group containing itself but would miss the same id reachable through two different paths.

### Structural sharing survived, and it had to be designed for

History snapshots are pointers into the document (`ADR 003`), so a derive pass that returned a fresh object every time - or cloned elements it did not change - would have turned one dragged rectangle into a full document copy per frame, on the write path, at 60fps.

`withDerivedGroups` returns its argument reference-identical when nothing changed. The gating is layered: a document with no groups returns immediately after one type check per element; `derivePass` skips a group whose box and membership already agree (`settled`); `withSingleHome` rebuilds `byId` only when a membership list actually changed, and returns the same `order` array otherwise. Two of those are subtler than they look:

- `filter` always allocates, so a box-only change had to avoid fabricating a fresh `childIds` array. `layerRows.ts`'s row memo compares every group's `childIds` by reference, and a new array on every pointermove of a grouped drag was exactly the "panel re-renders every frame" failure that structural sharing exists to prevent.
- `tree.ts` caches its parent index against `store.byId`, so keeping `byId` identical is not only about allocation - a fresh map would throw the index away on every write.

The comparison inside `derivePass` also uses a hand-written `sameNumber` rather than `===` or `Object.is`, and both rejections have a reason: `NaN === NaN` is false, so a non-finite box would never settle and would burn the fixed-point loop's full budget every write; and `Object.is(-0, 0)` is false, while `unionRects` can produce `-0`, so `Object.is` would turn a settled box into permanent churn.

### Inherited flags create a lock bypass that only exists once selection resolves upward

Canvas selection resolves to the outermost ancestor: clicking any member of a group selects the group. That is the right behaviour and it opens a hole. A locked member is not pickable on its own, but clicking an *unlocked* sibling resolves to the parent group, and expanding that selection to leaves would drag the locked member along with everything else.

Before this feature, `effectiveLocked` had **no production call site on the transform path** at all. `features/selection/gestureTargets.ts` is the one that closes it: `transformSet(...).filter(!effectiveLocked)`. Without it, a lock inside a group is decorative.

The module exists as its own seam rather than folding the filter into `transformSet` because `transformSet` has three callers with genuinely different lock policy. The properties panel deliberately still edits a locked element - that is how you restyle or unlock one - and alignment likewise. Folding `!effectiveLocked` into the shared expander would have made a locked element uneditable from the panel, a behaviour regression for the *ungrouped* case that nothing asked for.

That fix also changed the ungrouped case in a way worth stating: a locked element in a flat multi-selection used to be dragged along with the rest and is now left behind everywhere. Very probably the right semantics, but it was a real behaviour change and is now asserted directly in `store.test.ts` rather than assumed.

### Grouping is not free, and the derive pass is where the cost goes

Measured on the deliberately hostile shape - *every* element in one group, which maximises both `deriveGroupRect`'s descendant walk and the `byId` passes - driving the real store through `applyPatches` once per simulated drag frame, 60 frames per figure:

| elements | grouped commit | flat commit | `withDerivedGroups` alone |
| -------- | -------------- | ----------- | ------------------------- |
| 200      | 0.40 ms/frame  | 0.18        | -                         |
| 1 000    | 2.83 ms/frame  | 1.38        | 1.37 ms                   |
| 4 000    | 15.1 ms/frame  | 5.42        | 6.34 ms                   |

Roughly 2.8× the flat write cost at 4,000 elements, of which the derive pass is about 42%. A group-free document pays nothing measurable, because of the early return. A realistic document - a group of twenty inside a thousand elements - pays only for that group's subtree.

Nothing here was optimised, deliberately. If the 4,000-in-one-group case ever needs 60fps, the profitable target is `derivePass`, not the surrounding write machinery. The numbers are recorded so that decision starts from a measurement.

### Serialization went nested, which reverses an argument this project had already made

`docs/data-model.md` justified a flat export array on the grounds that an array is self-describing and cannot disagree with itself, while `{ byId, order }` can. Membership turns that argument around rather than weakening it: a flat array carrying `childIds` *can* now disagree with itself - an id listed inside a group and again at the root describes two different trees, and the loader would have to pick one. Nesting cannot express that state at all. Same principle, opposite conclusion, because the data changed. It also happens to mirror SVG's `<g>`, which is what the export already wanted.

`CURRENT_SCHEMA_VERSION` is 2 and the v1→v2 migration is near-identity, because a flat v1 `elements` array is already a valid v2 forest of roots with no children. It exists, is registered, and is tested anyway: a gap in the chain is a hard error, and "this version needs no work" is a claim that should be made explicitly rather than by omission. The chain was built and proven against a synthetic v0→v1→v2 sequence precisely so this would not be its first, unrehearsed use.

Nesting removes the dangling-reference and cycle classes from the *file* by construction, and adds exactly one new one: depth. `MAX_GROUP_DEPTH = 64` is enforced at both places a file becomes a document - `validate.ts` on the load path, and `projectRepository.ts`'s own raw walk, which summarizes records validation has not touched yet. It is not enforced on a third untrusted-input path: clipboard paste (`features/commands/clipboard.ts`) `JSON.parse`s arbitrary clipboard text and runs each element through `validateElement.ts`, which validates one element in isolation and has no notion of depth, so a pasted payload can build an arbitrarily deep tree that `tree.ts`, `layerRows.ts` and `serialize.ts` then recurse over. Known gap, follow-up work, not closed by this feature. Anything past the cap on the two covered paths is dropped and reported through the existing warnings channel, consistent with the drop-and-warn policy for malformed elements. Under nesting, one `seen` set also covers three failures at once - a duplicate at the root, one id claimed by two parents, and a group containing itself - because all three are "this id is already spoken for".

### Virtualization survived, by flattening rather than nesting

The layers panel windows a flat array of fixed-height rows, which is what took it from 45,231 DOM nodes to 538 (`docs/performance.md` §7). A tree could have broken that outright. `buildLayerRows` flattens the tree into `{ id, depth, hasChildren, expanded, parentId, indexInParent, siblingCount }` rows and skips the descendants of collapsed groups, so every row is still `LAYER_ROW_HEIGHT` tall and depth becomes indentation, which costs nothing vertically. The windowing arithmetic itself is untouched (`useVirtualRows.ts` has zero diff across the branch), and the roving tab stop carried over in a straight extraction (`useLayerFocus.ts`). The selection-follow effect did change: it gained `expandAncestorsOf` to unfold a collapsed ancestor before scrolling to it, and was split into two effects so the scroll waits for that taller render to actually commit (`LayersPanel.tsx`).

`aria-rowcount` now counts **visible rows** rather than total elements, and that is the correct meaning, not a compromise: a collapsed group's members are not reachable by arrow key, and counting them would misreport the list's length to a screen reader. The existing virtualization tests asserted the old meaning and were changed with the reason stated in the commit, not quietly.

Drag-reorder stopped being a single integer. In a tree a drop is a pair, `(parentId, index)`, and the same visual gap can mean several different parents - the gap below the last member of a group is also the gap below the group, and also the gap below whatever the group sits in. A group row resolves this from the pointer alone with no extra state, split three ways: outer quarters mean "beside this row", the middle half means "inside it". A leaf row has no inside to offer, so it splits 50/50 at its own midpoint instead - a deliberate fix in its own right, argued in `dropTarget.ts`'s `zoneAt` docblock. `dropTarget.ts` is pure over the row array, which matters because a refusal the store enforces but the indicator does not know about is an interface that draws a landing place for a drop that will not happen.

### View state stayed out of the document

`collapsedGroupIds` and `enteredGroupId` live in the `ui` slice, not on the element. On the element they would serialize into the saved file and enter history, making *expanding a group* an undoable action. That was decided up front and is the kind of thing that is very hard to unpick later, because by then something is persisting it.

## Known limitations

Recorded because they are real and reachable, not to pre-empt criticism.

- **Resizing a rotated group shears slightly.** Accepted, as above; the same limitation Figma has.
- **A group reduced to a single *rotated* leaf draws its resize handles offset from where they act.** The overlay measures the frame from the group's axis-aligned derived box (rotation 0) while the transform and the handle hit-test both use the leaf's own angle. The resize itself is correct and the two frames coincide whenever the sole leaf is unrotated, which is the common case. Closing it properly means the overlay reading the same set the transform does.
- **Alt+Arrow keyboard reorder refuses a nested row.** It speaks only about the root order, and a nested row's display index says nothing about a position in `order` - so it refuses rather than moving a row somewhere arithmetic happened to point. Reparenting is reachable only by pointer drag in the layers panel, which is a genuine accessibility gap in a panel whose whole justification is being the canvas's keyboard-navigable counterpart.
- **A group's `rotation` field, once set, is never rewritten by the derive pass - and nothing in the app writes one.** `derivePass` re-derives `x`/`y`/`width`/`height` and leaves `rotation` alone, while both routes to rotating a group patch its **leaves**: the canvas gesture (`executeIntents` → `rotateElements`) and the properties panel's angle field (`features/properties/rotation`). So the only way a group can carry a nonzero `rotation` is a value arriving from a file, where it persists on a group whose members never moved and is read by nothing but the serializer that wrote it.
- **Every field in the properties panel's Transform section is group-aware, and none of them writes to a group.** A patch naming a group's box is erased by `withDerivedGroups` inside the same synchronous write, so all five fields redirect to the leaves - the same redirection the canvas already performs for a frame drag, a handle pull and a rotate. **Angle** (`features/properties/rotation`) closed the field's original defect: it read `group.rotation`, the one number in the document nothing ever writes, so it said 0 while the group visibly turned. It now reads the leaves and turns the group as one rigid body about its centre by the delta `N - current`, the identical operation the rotation handle performs; leaves that disagree read "Mixed" and each take the typed angle in place, since a splayed group has no single current angle to subtract. **Position and Size** (`features/properties/geometry`) were originally disabled for a group and are no longer: X/Y translate the leaves so the derived box lands on the typed coordinate, and W/H scale them through `resizeElements`' multi-element branch, standing in for the canvas handle that moves the same axes: `e` for a width, `s` for a height, `se` when the aspect lock moves both. All three pin the frame's north-west corner, so the two fields the user did not touch keep their values; picking per axis rather than fixing `se` is what keeps a width-only edit from switching `autoHeight` off on the group's text leaves, since `releaseAutoHeight` reads "did this change the height?" off the handle. `features/properties/targets` decides which elements all five may land on - a group stands in for its unlocked leaves, a directly selected locked element is kept - so the section is disabled only when every member of the selection is a locked leaf, and even then it still *shows* the derived box.
- **A loose multi-selection sets each element's W to N; a group scales as a unit.** Two readings of the same field, and the asymmetry is inherited rather than introduced - it is exactly what the angle field already does (each loose element takes N in place, a group turns rigidly). A group is a named, persistent object with a box of its own, so "make it 200 wide" has an obvious referent; an ad-hoc multi-selection does not, and scaling one as a unit would make the field's meaning depend on how many things happen to be selected. Left as it is, and recorded here because the two behaviours are one control.
- **Scaling a group down can clamp its smallest member at `MIN_ELEMENT_SIZE` and distort the arrangement.** `resizeElements` applies the floor per leaf, so a member that reaches it stops shrinking while its siblings keep going, and the group's box no longer reaches the typed size. The clamp is deliberately left there rather than lifted to a floor on the whole group's scale: the resize handle clamps per leaf too, and a panel that clamped differently would make typing `W = 5` land somewhere other than dragging to 5. It costs nothing *within* a gesture - every event replays the frozen snapshot, so a scrub that squashes past the floor and comes back restores the original exactly - and only the boundary between two separate gestures is lossy, which is equally true of the handle. That guarantee shipped **half true** and is worth recording as such: the aspect lock's ratio was the one thing not frozen with the rest, computed in `PositionSection` from the values the fields were currently showing. A clamped leaf holds the group's union open in its axis, so with the lock on the coupled axis was divided by a height the previous event had inflated - the same 200 → 10 width edit landed at H = 9 typed and H = 6.7 over a hundred pointermove events, and an out-and-back left the group ~10% shorter. The ratio is now frozen alongside the leaves and the frame (`features/properties/geometry`'s `coupledPatch`), and the sentence above holds with the lock either way.
- **A transform edit is defined against the state its gesture started from, so it is one gesture at a time that agrees with the handle.** `rotationSnapshot` freezes the leaves, the pivot and the starting angle when the gesture begins - at `onScrubStart` for a label scrub, at the single `onChange` for a typed value - and every event replays the *absolute* target against that. This is the same shape as `executeIntents`' `GestureSnapshot`, and it has to be: a scrub fires ~100 `onChange` calls, and composing 100 deltas about a pivot re-measured each time walks an asymmetric group tens of world units off (`docs/problems-log.md` 008). What it does **not** make invariant is the pivot *across* gestures: a group's centre is the union of its leaves' rotated boxes, so 45° twice is not 90° once. That is true of the rotation handle over two drags as well, and it is a property of a derived pivot rather than of the field. `geometrySnapshot` is the same construction for Position and Size, where the failure it prevents is worse than drift: a width scrub that re-measured the group's box per event would divide each new target by a box its own previous event had just changed, so the scale would *compound* and the group would run away exponentially.
- **A panel scrub that travels out and comes back costs one undo entry that changes nothing.** Not grouping-specific and not new - it is true of X, Y, W, H, opacity and the angle field alike, and was verified on X for a loose rectangle. `commitTransaction` decides "did this gesture change anything?" by comparing the document to the opening snapshot **by reference**, and every intermediate write of the scrub mints fresh element objects, so restoring the exact numbers does not restore the pointer. A gesture that never moved is still correctly free - the scrub writes the same values, `patchDocument` returns the document untouched, and identity holds - so what is left is only the *moving* out-and-back, where Ctrl+Z is a no-op the user has to press once. Closing it is one content comparison in `features/history/transaction.ts`, deliberately not taken on this branch: it changes the no-op test for every transaction in the app, including the pointer gestures, and belongs in a change scoped to history rather than to grouping.
- **The first angle edit on a splayed group changes what the control means for the next one.** With the leaves disagreeing there is no `current` to subtract, so each leaf takes N *in place* - every centre stays put - and afterwards the leaves **agree**, which is precisely the condition for the rigid branch. So typing 45 and then 90 lands the group somewhere entirely different from typing 90 once, with nothing in the UI signalling that the operator changed under it. The in-place fallback is still the right behaviour: it is what the field already does for a mixed rotation across a loose multi-selection, it moves nothing, and it preserves the invariant that the field reads N afterwards - any alternative would have to invent a `current` out of one arbitrary leaf. The discontinuity is a consequence of "Mixed" having no single value, recorded here rather than papered over.
- **Deleting the selection while a panel scrub is in flight commits under the wrong label.** `edit.delete` gates only on `editable().length > 0` and `edit.clear-selection` (Escape) on `interaction.kind === 'idle'` - both true during a scrub, since a panel scrub never touches `interaction.kind`. If Delete fires instead of Escape, its write lands inside the still-open scrub transaction: `applyChange` at `depth > 0` only advances `present` (`features/history/transaction.ts:158-160`), so `commitTransaction` closes the gesture by pushing the transaction's own `pending.label` (`:116`) - and the pair ships as one undo entry labelled `Rotate`/`Move` instead of `Delete`. Undo is correct (one press restores both), so the cost is a wrong string in the undo tooltip after a rare two-handed gesture. Fixing it means the delete command refusing to run, or the transaction splitting, while a scrub is in flight - a command-layer change, out of scope here.
- **A selection change that leaves the Transform section mounted still replays the frozen snapshot against the old selection.** The teardown fix above only wires the gesture's *unmount* exit - Escape/Delete emptying the selection outright. Ctrl+A during a live scrub leaves the section mounted (a selection still exists), so `NumberField` never unmounts and its cleanup never runs; the ref keeps pointing at what `onScrubStart` captured, and every following `onChange` keeps patching those old elements - not the new selection - until a `pointerup`/`pointercancel` finally lands. This is true of **both** panel snapshots, identically: `rotationScrub.current` holds the leaves and the pivot, `geometryScrub.current` (added with the group-aware Position and Size fields) holds the leaves, the frame and the locked box, and both are cleared only in `endScrub`. Same family as the teardown hazard above, distinct trigger, not fixed here.
- **A keyboard nudge on another field while a scrub is held replays the scrub's snapshot.** One `geometryScrub` ref serves all four of X, Y, W and H, so tab-focusing the X input, holding a W scrub with the other hand and pressing an arrow key sends `{ x: N }` into the *width* gesture's snapshot. That patch has no scale, so it takes the pure-move branch - which writes the frozen extents back verbatim and therefore undoes however much of the width drag has landed so far; the next pointermove then replays the width from the same frozen frame and discards the nudge in turn. The two gestures overwrite each other rather than compose. Previous bullet's mechanism by a second route (one snapshot, two fields), needs two hands on purpose, and the honest fix is a snapshot per field - a wider change to how the section brackets a gesture than this ADR's subject warrants.
- **A height edit on a group releases `autoHeight` irreversibly within the gesture.** `groupPatches` reaches `resizeElements` - and so `releaseAutoHeight` - the moment a height patch scales the leaves, correctly clearing the flag on an auto-height text leaf. But the branch a zero-delta or out-and-back patch takes (`scaleX === 1 && scaleY === 1`, the pure-move path) restores width and height verbatim without restoring anything `resizeElements` cleared earlier in the same gesture. Measured: a height scrub 20 → 5 → 80 → back to 20 leaves `autoHeight: false` on a leaf that started `true`. Undo *does* restore it, since it rides the transaction, so the loss is within-gesture only - nothing survives to the next commit. The right fix is a general "restore what the gesture released" in the patch/verbatim-restore machinery, not a special case for this one flag, which is why it is recorded here rather than patched.
- **The loose-element path never releases `autoHeight` at all.** `geometryPatches`' `entry.kind === 'element'` branch sends a single selected element's patch through `applicablePatches`, not `resizeElements` - and `applicablePatches` has never called `releaseAutoHeight`. So typing a height on one auto-height text box sets it, and the next keystroke that re-measures the text recomputes the height away. Genuinely pre-existing - this branch did not touch `applicablePatches` - but now that the group path above calls `releaseAutoHeight`, this is the only remaining place the panel and the canvas disagree about the flag.
